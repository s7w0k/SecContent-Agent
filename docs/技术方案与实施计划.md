# 智能体安全PR情报Agent系统 — 技术方案与实施计划

## Context

基于现有的 `wewe_mcp`（微信公众号RSS MCP服务）和 `site_crawl`（海外安全新闻爬虫），构建一个完整的端到端Agent系统，实现从**内容爬取 → 入库 → Agent分析打分 → PR报道生成 → 可视化展示**的全链路自动化Demo。

## 服务划分

| 服务 | 端口 | 技术栈 | 说明 |
|------|------|--------|------|
| `mongodb` | 27017 | MongoDB 7 | 数据持久化（文章原文、分析结果、PR报告） |
| `mcp-wewe` | 8100 | FastAPI + MCP | 微信公众号RSS MCP HTTP桥接（复用现有wewe_mcp） |
| `mcp-crawl` | 8101 | FastAPI + MCP | 海外安全新闻爬虫 MCP HTTP桥接（封装site_crawl） |
| `backend` | 8000 | FastAPI + LangChain | 核心后端：Agent编排、REST API、静态文件服务 |
| `frontend` | 5173(dev) | React + Ant Design | 可视化仪表盘（生产构建由backend托管） |

## 详细设计

### 1. mcp-wewe 服务（复用现有代码）

**文件**: `wewe_mcp/http_mcp_bridge.py`（现有，微调）

- 与现有 `http_mcp_bridge.py` 基本一致
- 增加健康检查端点 `GET /health`
- 作为独立容器运行，通过 `WEWE_RSS_URL` 环境变量配置目标
- 提供8个MCP工具：账号管理5个 + RSS分析3个

### 2. mcp-crawl 服务（新建，封装site_crawl）

**新建文件**: `services/mcp_crawl/`
```
services/mcp_crawl/
├── __init__.py
├── server.py          # MCP Server (stdio JSON-RPC, 与wewe_mcp_server.py同模式)
├── http_bridge.py     # FastAPI HTTP桥接 (与http_mcp_bridge.py同模式)
├── requirements.txt
└── Dockerfile
```

**MCP工具列表**:
| 工具名 | 功能 |
|--------|------|
| `crawl_news` | 爬取海外安全新闻（支持天数参数） |
| `classify_articles` | AI分类文章（AI安全/Agent安全） |
| `query_database` | 查询已爬取的文章数据库 |
| `get_stats` | 获取爬取统计信息 |
| `export_csv` | 导出AI安全文章CSV |

实现方式：从 `site_crawl/crawl_classify_persistent.py` 提取 `NewsCrawler` 和 `AISecurityClassifier` 类，封装为MCP工具函数。

#### 3.1 Agent流水线设计（LangGraph）

```
START
  │
  ▼
[crawl_phase] ──────────────────────────────────────
  │  调用 mcp-wewe: fetch_yesterday_articles        │
  │  调用 mcp-crawl: crawl_news                     │
  │  对每篇文章调用 fetch_article_fulltext           │
  │  存入 MongoDB (articles collection)             │
  └─────────────────────────────────────────────────
  │
  ▼
[classify_phase] ───────────────────────────────────
  │  调用 mcp-crawl: classify_articles              │
  │  更新 MongoDB 中文章的分类字段                    │
  └─────────────────────────────────────────────────
  │
  ▼
[score_phase] ──────────────────────────────────────
  │  加载产品知识库（docs/产品计划.md）              │
  │  LLM对每篇文章打分：                             │
  │    - ai_relevance_score (0-100): 与产品相关度    │
  │    - reportability_score (0-100): 可报道性      │
  │    - score_reason: 打分理由                      │
  │  更新 MongoDB                                   │
  └─────────────────────────────────────────────────
  │
  ▼
[report_phase] ─────────────────────────────────────
  │  筛选高分文章 (如总分≥140)                       │
  │  LLM按结构化PR模板生成报道                       │
  │    - 标题 + 导语 + 背景 + 分析 + 影响 + 建议     │
  │  存入 MongoDB (reports collection)              │
  └─────────────────────────────────────────────────
  │
  ▼
END → 前端可查看结果
```

#### 3.2 PR报道模板

```markdown
# [情报标题]

## 导语
[2-3句话概述事件核心]

## 背景
[事件发生的背景信息、涉及厂商/技术]

## 分析
[结合产品能力的技术分析，为什么对智能体身份安全重要]

## 影响评估
[对行业/客户/竞品的潜在影响]

## 行动建议
[产品侧可采取的应对建议]
```

#### 3.3 打分维度

| 维度 | 分值 | 说明 |
|------|------|------|
| AI/Agent安全相关度 | 0-100 | 与产品覆盖领域（身份安全、权限管控、意图防护等）的匹配度 |
| 可报道性 | 0-100 | 新闻价值：是否新技术/重大漏洞/竞品动态/客户相关/行业趋势 |
| 综合分 | 0-200 | 两项之和，≥140 触发PR报道生成 |

#### 3.4 知识库设计

- 来源：`docs/智能体身份安全产品计划和目标.md`
- 加载方式：启动时读取，作为System Prompt注入打分和报道Agent
- 关键提取内容：产品定位、技术壁垒（6大独创功能）、控标点（16项）、客户案例
- 打分时Agent参照知识库判断文章与产品的匹配度

### 6. REST API 设计

```
GET    /api/health                    # 健康检查
GET    /api/articles                  # 文章列表（分页+筛选+排序）
       ?page=1&page_size=20
       &source_type=overseas_news
       &category=MCP
       &min_score=100
       &date_from=2026-06-01
       &date_to=2026-06-26
       &sort_by=added_at&order=desc
GET    /api/articles/:hash            # 单篇文章详情（含原文markdown）
GET    /api/stats                     # 统计概览（总数/分类分布/来源分布/分值分布）
POST   /api/pipeline/run              # 触发完整流水线
       {"crawl_days": 1, "phases": ["crawl","classify","score","report"]}
POST   /api/pipeline/crawl            # 仅爬取
POST   /api/pipeline/score            # 仅打分（对已入库文章）
POST   /api/pipeline/report           # 仅生成报道（对高分文章）
GET    /api/pipeline/status           # 流水线运行状态
GET    /api/reports                   # PR报道列表
GET    /api/reports/:id               # PR报道详情
GET    /api/knowledge                 # 知识库摘要
```

## 关键技术决策

1. **MCP通信方式**: HTTP Bridge模式（非stdio），适合Docker多容器部署
2. **Agent框架**: LangGraph（状态图编排），比ReAct Agent更适合多阶段流水线
3. **LLM选择**: DeepSeek（统一使用，已经在两个模块中验证可行）
4. **前端构建策略**: 开发时Vite dev server（:5173），生产构建由FastAPI托管静态文件（单一8000端口）
5. **MongoDB选型理由**: 文档型存储天然适合Markdown内容；相比JSON文件，支持复杂查询和分页

## 验证方案

1. **单元验证**: 各MCP工具独立可调用，返回正确结果
2. **流水线验证**: `POST /api/pipeline/run` 触发后，检查MongoDB中articles/reports数据完整性
3. **前端验证**: 仪表盘表格正确展示数据，筛选/排序/分页正常
4. **Docker验证**: `docker compose up` 一键启动所有服务，8000端口可访问完整系统
5. **端到端验证**: 模拟完整场景：爬取 → 入库 → 打分 → 生成报道 → 前端查看
