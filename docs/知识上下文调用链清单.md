> 依据《知识库检索策略改造逐步实施方案》阶段0 S0-1
> 目标：在改代码前列出所有会**生成或修改 PR 内容**的入口，记录每个入口当前的产品来源、知识入口与 fallback，为后续阶段建立改造基线。

范围说明：本清单聚焦"会生成或修改 PR 内容"的入口；仅抓取/入库（不产生 PR 正文）的海外新闻服务也有记录，但标记为"间接入口"。

## 2. 逐入口明细

### E1 单篇 `run-v2`（单文章智能 PR 流水线）

- **入口代码**：`api/pipeline.py::run_v2_single`（路由）→ `_run_v2_single_workflow`（后台任务）
- **流程**：分类 → 评分（`scorer_v2.score_single`）→ 若 `is_pr_candidate` 则生成个性化草稿（`draft_gen.generate`）
- **当前产品来源**：
  - 复用文章已存分数：`article["product_relevance"]`、`article["pr_total_score"]`
  - 分数缺失时调用 `scorer_v2.score_single` 重新评分
  - 产品 ID 未在单篇草稿阶段显式冻结；`task_doc["generation_options"]` 仅用于 `draft_variants` 等选项，未保存产品路由结果
- **知识入口**：
  - 评分阶段：`scorer_v2` 内部（`KnowledgeSliceResolver` 按产品 ID 构建知识切片）
  - 草稿阶段：`draft_gen.generate` 内部加载知识切片；同时存在 `ContextBridge` shadow 草稿（`[run-v2-single] ContextBridge shadow draft` 日志）
- **fallback**：评分/草稿知识切片失败时回退全局知识（`knowledge.as_system_prompt()` 路径），见 `[run-v2-single] knowledge slice failed` 日志
- **改造关注点**：单篇草稿阶段未使用冻结的产品路由快照，产品知识依赖评分时隐式解析，存在"评分知道产品、草稿推断产品"的断链风险（阶段2 修复）。

### E2 批量 `run-v2`

- **入口代码**：`api/pipeline.py::pipeline_run_v2` → 入队 → worker 按 `worker_registry` 节点执行 `pipeline_v2.*`
- **流程**：crawl → enrich → classify → filter → score → draft → quality_check → rewrite → review
- **当前产品来源**：评分节点产出 `article["product_relevance"]` 等；草稿节点按 `pr_total_score >= score_threshold` 遍历文章，使用文章已存分数
- **知识入口**：`draft_node` 内 `knowledge.load()` + `draft_gen.generate`；`rewrite_node` 类似
- **fallback**：全局知识（`knowledge.as_system_prompt()`）
- **改造关注点**：批量与单篇对同一文章应得到相同产品快照（阶段2 一致性校验目标）。

### E3 `pipeline_v2` 草稿节点

- **入口代码**：`agent/pipeline_v2.py::draft_node`（`worker_registry` 注册为 `"draft"`）
- **当前产品来源**：`art["product_relevance"]`、`art["event_impact"]`、`art["pr_total_score"]`（`v2_scores`）
- **知识入口**：`knowledge.load()` + `draft_gen.generate(art, v2_scores, ...)`
- **fallback**：全局知识；无产品显式路由

### E4 `pipeline_v2` 质量重写节点

- **入口代码**：`agent/pipeline_v2.py::rewrite_node`
- **当前产品来源**：沿用草稿阶段确定的产品/分数（重写不重新路由）
- **知识入口**：同草稿（复用产品知识上下文）
- **fallback**：全局知识
- **改造关注点**：`rewrite_node` 应复用原草稿产品快照，不重新猜测产品（阶段2 S2-3/S2-4）。

### E5 定时海外新闻流程（间接入口）

- **入口代码**：`agent/overseas_news_service.py::OverseasNewsIngestionService.run`（手动抓取与定时抓取共用）
- **职责**：mcp-crawl 抓取 → 规范化 → 原子 upsert 到 `articles` → 提交全文任务（`fetch_fulltext_batch`）
- **当前产品来源**：**无**——入库阶段不进行产品路由，文章以 `source_type=overseas_news` 落库，产品判定发生在后续管线评分阶段
- **知识入口**：不注入知识（仅入库）
- **fallback**：不适用
- **改造关注点**：作为 PR 生成的**间接入口**，其落库文章最终进入 E2 批量管线；产品路由应在后续评分阶段统一处理，无需在入库阶段重复。

### E6 草稿问答

- **入口代码**：`agent/draft_chat.py::answer`（含 `_answer_legacy` / `_answer_agent` 双路径）
- **当前产品来源**：Prompt 中注入 `article.get("product_relevance")` 等分数（`_build_article_context`）
- **知识入口**：`_get_knowledge_prompt()` → `knowledge.as_system_prompt()`（**全局知识库**，非按产品切片）
- **fallback**：`（知识库未加载）` 占位文本
- **改造关注点**：问答路径使用全局知识而非冻结产品知识，`as_system_prompt()` 为阶段3 要收紧的"受控兼容路径"。

### E7 局部改稿

- **入口代码**：`agent/draft_chat.py::revise`；`selected_text` 非空时进入局部改写（`SECTION_REVISE_*` prompt）
- **当前产品来源**：Prompt 注入 `article` 字段（`product_relevance` 等）
- **知识入口**：`_get_knowledge_prompt()` → `knowledge.as_system_prompt()`（全局）
- **fallback**：`（知识库未加载）`

### E8 流式改稿

- **入口代码**：`agent/draft_chat.py::stream_revise`
- **当前产品来源/知识入口/fallback**：与 E7 一致（`REVISE_SYSTEM_PROMPT` / `SECTION_REVISE_SYSTEM_PROMPT` + 全局知识）

### E9 旧 `ReportAgent`

- **入口代码**：`agent/reporter.py::ReportAgent`；构造于 `worker.py`、`main.py`
- **当前产品来源/知识入口**：`ReportAgent(llm=..., knowledge=knowledge._cache, db=...)`，知识来自全局缓存
- **状态**：**仍被构造**，需确认是否仍有生产调用；若已废弃应在阶段3 前明确下线或标记兼容。

## 5. 阶段1 接线状态（产品自动路由）

阶段1 完成"修复产品自动路由"，产出了新的统一解析入口，供后续阶段接线：

- **统一解析入口**：`agent/product_routing.py::ProductRoutingService.resolve(article, mode, selected_product_ids, user_id)`
  - `selected`：严格按用户选择，不调用自动匹配；
  - `auto`：`ProductMatcher.match_by_rules()` 规则召回 + 可选 `LLMProductReranker` 重排；
  - `none`：返回空产品。
  - 返回 `ProductRoutingSnapshot`（含 `ambiguous` / `confidence`）。
- **规则召回**：`agent/product_matcher.py` 分字段加权（标题 30 / 摘要 20 / 正文 10，产品名/别名 40/25/15），空白归一化，弱词降权。
- **目录收敛**：`agent/product_catalog.py::ProductEntry` 新增 `keywords`，matcher 优先使用目录关键词；`published_only=True` 确保未发布产品（agent-security-gateway / ans）不进入 auto 路由。
- **评测**：83 条用例上 Top1 100%、Top2 100%（门禁 ≥90% / ≥97%），见 `tests/agent_evals/knowledge_retrieval/`。

> 本阶段仅产出路由原语；E1-E9 入口仍未使用冻结路由快照（阶段2 接入）。

## 6. 阶段2 接线状态（产品路由结果贯穿 PR 流水线）

阶段2 完成"消除『评分知道产品、草稿不知道产品』断链"，将冻结路由快照贯穿各 PR 生成入口：

- **S2-1 任务创建时冻结路由**：`agent/pipeline_config.py::PipelineConfigFreezer.freeze()` 对 selected/auto/none 统一调用 `ProductRoutingService.resolve()`，快照新增 `routing` / `routing_version` / `knowledge_source_ids` / `knowledge_fallback`；auto 无命中时 `knowledge_fallback="product_unresolved"`。
- **S2-2 评分使用冻结候选**：`agent/scorer_v2.py::_score_concurrent` 逐产品构建评分知识上下文，聚合后明确 `best_product_id`（按 relevance 取最高）。
- **S2-3 草稿使用最终产品快照**：`api/pipeline.py::_run_v2_single_workflow` 在 `is_pr_eligible` 时冻结路由，评分传 `products`，草稿用 `frozen_product_ids`（优先级 selected 冻结 > auto 冻结 > best_product > unresolved），禁止仅从 `selected_product_ids` 推断 auto 产品。
- **S2-4 补齐批量和重写路径**：`agent/pipeline_v2.py::draft_node`/`rewrite_node` 按文章解析路由并传 `knowledge_slice`；重写沿用原草稿 `routing_meta.resolved_products`，不重新路由（旧草稿无元数据时按 auto 兼容解析）。
- **S2-5 草稿保存产品与知识元数据**：批量草稿与单篇草稿均保存 `routing_meta`（含 `resolved_products` / `routing_version` / `knowledge_source_ids` / `knowledge_fallback`）。

## 7. 阶段3 接线状态（统一知识上下文入口）

阶段3 通过 ContextBridge 统一各 PR 内容生成入口的知识获取，旧全局 prompt（`as_system_prompt`）只作为受控兼容路径。

- **S3-1 统一请求模型**：`agent/context_manager.py::ContextRequest` 新增 `task_id` / `trace_id` / `index_version`；`ContextBridge.build_plan` / `resolve_knowledge` 透传并写入 `ContextRequest.metadata`，可据此还原每次上下文来源。
- **S3-2 阶段化 query**：新增 `agent/context_queries.py`，含 `build_score_query` / `build_draft_query` / `build_rewrite_query` / `build_chat_query`，各带 400 字符上限。
- **S3-3 接入全部生成入口**：
  - `scorer_v2._build_system_prompt_for_product`：query=`build_score_query`，透传 task_id/trace_id；
  - `api/pipeline.py` 单篇 run-v2：query=`build_draft_query`，透传 task_id/trace_id；
  - `pipeline_v2._build_product_knowledge_slice`：active 模式优先经 ContextBridge，回退切片解析；
  - `draft_chat`：query=`build_chat_query`，透传 run_context 的 task_id/trace_id；
  - `reporter.generate_report`：经 `_build_context_plan` 优先用 ContextBridge（active 命中时替代全局知识）。
- **S3-4 收紧 fallback**：`context_bridge.py` 定义 `FALLBACK_*` 原因常量与 `allow_global_product_fallback()`；`product_unresolved` / `required_knowledge_missing` 禁止回退全局产品知识。
- **S3-5 统一 telemetry**：`_telemetry` 新增 `task_id` / `trace_id` / `products` / `source` / `fallback`，不含知识全文。

## 8. 阶段4 接线状态（轻量文档索引）

阶段4 建立可版本化、可增量更新、可追溯的 JSON 索引，**不改变 active 检索行为**（仅新增元数据能力，供阶段5 自适应召回使用）。

- **S4-1 索引 schema**：新增 `agent/knowledge_index.py`，定义 `KnowledgeIndexManifest / DocIndex / SectionIndex`，`SCHEMA_VERSION=1`，兼容读取（`KnowledgeIndexer` 按结构读取，允许更高 schema 版本），确定性序列化（`index_version` 排除时间戳，相同输入哈希稳定）。
- **S4-2 文档发现和分类**：产品目录映射来自 `ProductCatalogService`；`overview/market-brief`→required，`sales-brief/architecture-brief/tasks`→optional，`原始文档/`→raw/fallback，`shared/`、`0-产品全景/`→shared；`skills/_index/海外版` 及根级 `AGENTS/CLAUDE/README/qa-log` 排除；未发布产品文档入索引但 `published=False`。
- **S4-3 description/summary 生成**：规则摘要（确定性）+ 可选离线 LLM 长 raw 文档章节摘要（`KnowledgeIndexBuilder(llm_summarizer=...)`，失败回退规则）；`validate()` 做 schema 与事实约束校验（必需 brief 可定位、路径安全、doc_id 唯一）。
- **S4-4 增量构建**：基于 `content_hash` 只重建变化文档、复用旧元数据；删除文档从 manifest 移除；临时文件 + `os.replace` 原子写入。
- **S4-5 发布流程对接**：`knowledge_admin/publication.py::publish()` 发布前用内容覆盖构建并校验索引（失败即中止，不覆盖线上知识），发布成功后原子写入索引版本；`rollback()` 回滚后重建索引；`agent/knowledge_runtime.py` 新增 `get_index_version()` 供任务边界加载新版本。
- **配置**：`config.py` 新增 `KNOWLEDGE_INDEX_PATH` / `KNOWLEDGE_RETRIEVAL_ENABLED` / `KNOWLEDGE_RETRIEVAL_SHADOW_ENABLED` / `KNOWLEDGE_RETRIEVAL_ROLLOUT_PERCENT` / `KNOWLEDGE_LLM_RERANK_ENABLED` / `KNOWLEDGE_EMBEDDING_ENABLED` / `KNOWLEDGE_MAX_OPTIONAL_DOCS` / `KNOWLEDGE_MAX_EXPANDED_SECTIONS`。

## 16. 阶段8 检索排序指标优化（中文分词 + 章节覆盖 + embedding 混合召回）

针对第15节真实 query 指标偏低（Recall@1=16.9%）做的全链路分析与优化。

### 根因定位

1. **中文整词匹配、无分词**：`_tokenize` 按空白/标点切分，中文 query 整句成一个 token（如 `智能体身份认证方案` 整体），无法匹配文档子词。`_keyword_score` 用 `term in title/summary` 整词子串匹配，query 与文档用词不同时打 0 分。→ 修复：`_tokenize` 引入 jieba 分词（`cut_for_search`），jieba 不可用时回退原规则。
2. **打分字段不覆盖正文**：`_keyword_score` 只看 title/keywords/description/summary，答案藏在章节正文的文档无法召回。→ 修复：新增 `_section_searchable_text`，把各章节 title+summary 纳入打分（权重 0.5）。
3. **raw/shared 噪声污染排序（关键）**：`_hard_filter` 无条件放行 raw/shared，其巨正文本得分虚高、抢占前排，把真正相关的 core 文档挤出 Top5；且相关集合只含 core 类型。修复前 Recall@3=46.0% FAIL。→ 修复：`retrieve_ranked` 仅对 core（allowed types）文档排序，排除 raw/shared。修复后 Recall@3=64.4% PASS。
4. **无语义召回**：仅 BM25 关键词，无法处理同义表达。→ 修复：接入 DASHSCOPE `text-embedding-v3`（1024 维），`embedding_provider.py` 提供 `build_embedding_store` + 混合权重调优。

### 优化结果（真实线上 Query，87 条有相关样本）

| 指标 | 初版(纯BM25+噪声) | 步骤2(分词+章节) | **最终(embed=0.3)** |
|---|---|---|---|
| Recall@1 | 16.9% | 17.7% | **23.1%** |
| Recall@3 | 46.0% | 64.4% | **66.9%** |
| Recall@5 | 66.0% | 79.4% | **80.4%** |
| MRR | 0.721 | 0.850 | **0.865** |
| HitRate@3 | 81.6% | 92.0% | **92.0%** |
| 门禁 | 3 FAIL | 全 PASS | **全 PASS** |

最大单项收益来自**排除 raw/shared 噪声**（Recall@3 46→64），其次是 jieba 分词 + 章节覆盖（Recall@3 46→53），embedding 提供小幅稳定增益。

### LLM 重排（步骤4）结论：本场景下有害，保持关闭

实测 `--rerank`（DEEPSEEK 对 Top-N 带 title+summary snippet 重排）把 Recall@3 从 64.4% 拖到 33.7%（HitRate@3 92%→40%），且无失败回退日志（重排成功执行但排错）。原因：同产品 3 个文档（overview/market/sales）内容高度相似，LLM 无法区分哪个更相关，反而打乱 BM25/embedding 的正确排序；`top_n_rerank` 把窗口后文档补到末尾也可能挤出相关文档。

**结论**：LLM 重排更适合"单具体相关文档 + 语义差异大"的场景（如 RAG 问答），对"产品级多相关文档 + 文档高度同质"的检索排序有害，应在该用途下保持关闭（`KNOWLEDGE_LLM_RERANK_ENABLED=false`）。重排器能力本身已就绪（含内容注入），可留待更细粒度场景启用。
