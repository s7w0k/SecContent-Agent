# 产品知识库检索策略改造逐步实施方案

> 依据：《知识库检索策略改造方案.md》  
> 目标：以小步、可测试、可灰度、可回滚的方式完成产品路由闭环、统一知识上下文入口、轻量索引和章节级证据展开  
> 非目标：首期不引入向量数据库，不一次性删除全部旧接口，不在在线请求链路生成 LLM 摘要

---

## 1. 实施总览

```text
阶段 0：建立基线和契约
  ↓
阶段 1：修复并冻结产品路由
  ↓
阶段 2：让产品结果贯穿所有 PR 生成路径
  ↓
阶段 3：统一 ContextBridge 上下文入口
  ↓
阶段 4：建立轻量文档索引
  ↓
阶段 5：接入自适应文档召回
  ↓
阶段 6：建立章节级 lazy 展开和证据引用
  ↓
阶段 7：评测、shadow、灰度和全量
  ↓
阶段 8：按数据决定 LLM 重排/embedding
```

任何阶段未达到退出条件，不进入下一阶段的 active 模式。

---

## 2. 全局工程约束

### 2.1 唯一业务入口

评分、草稿、重写和改稿最终统一调用：

```text
ContextBridge
  → KnowledgeSliceResolver
  → KnowledgeIndex/DocumentRetriever
  → ContextManager
```

业务代码不得直接读取知识库路径并自行拼 prompt。

### 2.2 兼容与开关

建议新增或细化以下配置：

```text
KNOWLEDGE_RETRIEVAL_ENABLED=false
KNOWLEDGE_RETRIEVAL_SHADOW_ENABLED=true
KNOWLEDGE_RETRIEVAL_ROLLOUT_PERCENT=0
KNOWLEDGE_INDEX_PATH=/app/docs/_index/kb-index.json
KNOWLEDGE_LLM_RERANK_ENABLED=false
KNOWLEDGE_EMBEDDING_ENABLED=false
KNOWLEDGE_MAX_OPTIONAL_DOCS=6
KNOWLEDGE_MAX_EXPANDED_SECTIONS=2
```

如能复用现有 `KNOWLEDGE_SKILLS_*` 开关，应明确模式组合，避免两个灰度百分比互相覆盖。推荐以 `ContextBridge` 的开关作为总开关，检索开关控制其内部策略。

### 2.3 测试要求

每个阶段至少包含单元测试、关键链路集成测试、selected/auto/none 三模式、用户知识隔离、失败和回退测试，以及 trace 不泄露知识全文测试。

## 3. 阶段 0：基线、数据契约和评测集

### 3.1 目标

在改代码前冻结当前行为和目标契约，使后续能判断产品匹配、知识命中和 PR 质量是否改善。

### 3.2 任务

#### S0-1 建立链路清单

列出所有会生成或修改 PR 内容的入口：

- 单篇 `run-v2`；
- 批量评分/草稿；
- `pipeline_v2` 草稿和质量重写；
- 定时海外新闻流程；
- 草稿问答、局部改稿、流式改稿；
- 旧 `ReportAgent`，确认是否仍在生产使用。

产物：`docs/知识上下文调用链清单.md`，记录每个入口当前产品来源、知识入口和 fallback。

#### S0-2 定义产品路由契约

在模型层定义：

```python
class ResolvedProduct(BaseModel):
    product_id: str
    product_name: str
    match_score: int
    match_reason: str
    match_source: Literal["user_selected", "rule", "rule+llm"]

class ProductRoutingSnapshot(BaseModel):
    mode: Literal["selected", "auto", "none"]
    resolved_products: list[ResolvedProduct]
    routing_version: str
    resolved_at: datetime
```

明确保存位置：优先放入 `PipelineConfigSnapshot`，用户级单篇评分结果同时保存副本或稳定引用。

#### S0-3 建立离线评测集

首批建议 60–100 条：三个已发布产品各 15 条正例、10 条产品间歧义文章、10 条无产品命中文章、5–10 条跨产品文章、10 条需要原始文档章节支持的问题。

字段：

```json
{
  "case_id": "route-001",
  "article": {},
  "mode": "auto",
  "expected_product_ids": ["ai-bom"],
  "required_doc_ids": [],
  "forbidden_product_ids": ["agent-security"],
  "requires_expansion": false,
  "allowed_product_claims": []
}
```

#### S0-4 记录旧链路基线

记录每阶段知识上下文字符/token、当前产品匹配、PR 产品事实和来源、单篇/批量/改稿差异，以及 LLM 调用次数和耗时。

### 3.3 主要文件

- `services/backend/models/generation_config.py`
- `services/backend/models/article_assessment.py`
- `tests/agent_evals/knowledge_retrieval/`
- `scripts/run_eval_harness.py` 或新建专用 runner

### 3.4 测试

- 路由快照 JSON 序列化稳定；
- `routing_version` 输入相同则一致；
- mode 与产品列表约束正确；
- 旧任务缺少新字段时可兼容读取。

### 3.5 退出条件

- 数据契约评审通过；
- 所有 PR 入口有清单；
- 至少 60 条标注用例；
- 旧链路指标可重复运行。

## 4. 阶段 1：修复产品自动路由

### 4.1 目标

让 auto 模式能基于文章真实字段产生可信的 Top 1–2 产品结果；selected/none 模式行为严格确定。

### 4.2 任务

#### S1-1 修复文章文本提取

修改 `product_matcher.py::_extract_text()`，按优先级读取 `title/summary_cn/summary/content_md/category_v2/tags/source`。设置最大长度，避免将 5 万字符全文直接交给路由器。

#### S1-2 收敛产品元数据

将产品关键词、别名和 description 收敛到 `ProductCatalogService` 或可发布配置中。短期保留 `_PRODUCT_KEYWORDS` 时，增加目录一致性测试，确保所有已发布产品有关键词、未发布产品不进入正式 auto 路由。

#### S1-3 增加置信度和歧义判断

- 明确产品名/唯一别名命中：高权重；
- 标题命中高于摘要，摘要高于正文；
- 通用词如“供应链安全”不能单独形成高置信产品命中；
- Top1 低于阈值或 Top1/Top2 分差过小，标记为 ambiguous。

#### S1-4 增加可选 LLM 产品重排器

LLM 只接收文章短摘要和最多 3–5 个候选产品的 ID、名称、description、命中关键词。严格使用 JSON schema，失败时回退规则结果，不允许创造目录中不存在的产品 ID。

#### S1-5 selected/auto/none 统一解析

实现单一 `ProductRoutingService.resolve()`：

```python
async def resolve(
    article: dict,
    mode: ProductTargetMode,
    selected_product_ids: list[str],
    user_id: str,
) -> ProductRoutingSnapshot:
    ...
```

### 4.3 主要文件

- `services/backend/agent/product_matcher.py`
- `services/backend/agent/product_catalog.py`
- `services/backend/agent/pipeline_config.py`
- 可新增 `services/backend/agent/product_routing.py`
- `services/backend/models/generation_config.py`

### 4.4 测试

- `summary_cn/content_md` 确实参与路由；
- 产品名、英文别名、缩写命中；
- 通用词不会错误高置信；
- selected 不调用自动匹配；
- none 返回空列表；
- LLM 返回非法产品 ID 被拒绝；
- LLM 失败回退规则结果；
- 用户产品严格按 `user_id` 隔离。

### 4.5 退出条件

- Top-1 准确率 ≥90%；
- Top-2 召回率 ≥97%；
- selected/none 确定性测试 100% 通过；
- 未发布产品不会进入正式结果。

## 5. 阶段 2：产品路由结果贯穿 PR 流水线

### 5.1 目标

消除“评分知道产品、草稿不知道产品”或“单篇与批量产品不同”的断链。

### 5.2 任务

#### S2-1 在任务创建时冻结产品路由

调整 `PipelineConfigFreezer.freeze()`：selected 立即校验并冻结；auto 有文章时立即解析并冻结；none 冻结空列表；保存 `routing_version` 和 `knowledge_hash/index_version`。

单篇 `run-v2` 当前直接保存原始 `generation_options`，应改为保存正式 `config_snapshot`，或至少保存等价的冻结路由结果。

#### S2-2 评分阶段使用冻结候选

调用 `scorer_v2.score_single(..., products=...)`，确保逐产品构建评分知识上下文并产出 `product_scores`。聚合后按 relevance 排序、明确 `best_product_id`，避免事件影响力因并发重复计算产生不稳定结果。

#### S2-3 草稿阶段使用最终产品快照

产品来源优先级：

```text
用户 selected 冻结结果
  > auto 冻结结果
  > 本次逐产品评分的 best_product
  > unresolved（不使用全局产品能力）
```

禁止仅从请求里的 `selected_product_ids` 推断 auto 模式产品。

#### S2-4 补齐批量和重写路径

在 `pipeline_v2.draft_node()`、`pipeline_v2.rewrite_node()`、批量生成 API 和定时任务后续生成入口中传入同一产品知识上下文。

#### S2-5 草稿保存产品与知识元数据

```json
{
  "resolved_products": [],
  "routing_version": "...",
  "knowledge_index_version": "...",
  "knowledge_source_ids": [],
  "knowledge_fallback": null
}
```

### 5.3 主要文件

- `services/backend/api/pipeline.py`
- `services/backend/agent/pipeline_config.py`
- `services/backend/agent/scorer_v2.py`
- `services/backend/agent/pipeline_v2.py`
- `services/backend/agent/task_queue.py`
- `services/backend/models/article.py`
- `services/backend/models/article_assessment.py`

### 5.4 测试

- auto 单篇：路由产品进入 score 和 draft；
- selected 单篇：只出现选择产品；
- none 单篇：无产品知识；
- 批量与单篇对同文章得到相同产品快照；
- 重写沿用原草稿产品，不重新路由；
- 跳过评分复用旧分数时仍能获取产品快照；
- 旧数据没有产品快照时走可观测兼容策略。

### 5.5 退出条件

- 所有草稿均保存 `resolved_products`；
- auto 草稿不再因空 `selected_product_ids` 丢失产品；
- 单篇、批量、重写产品一致率 100%；
- 不再静默回退到跨产品知识。

## 6. 阶段 3：统一知识上下文入口

### 6.1 目标

所有 PR 内容生成入口通过 `ContextBridge` 获取知识，旧全局 prompt 只作为受控兼容路径。

### 6.2 任务

#### S3-1 为 ContextBridge 定义统一请求

请求至少包含 `purpose/user_id/resolved_product_ids/query/model_id/task_id/trace_id/index_version`。

#### S3-2 构造阶段化 query

实现：

- `build_score_query(article)`；
- `build_draft_query(article, template, perspective)`；
- `build_rewrite_query(article, draft, issue)`；
- `build_chat_query(instruction, article, draft)`。

#### S3-3 接入全部生成入口

覆盖 `scorer_v2`、`draft_generator` 调用方、`pipeline_v2` 草稿/重写、`draft_chat` ask/revise/stream_revise 和仍启用的 `reporter`。`DraftGenerator` 可继续接收已解析的 `knowledge_slice`，但不负责自己检索。

#### S3-4 收紧 fallback

定义 `index_unavailable/context_build_failed/legacy_task_missing_snapshot/required_knowledge_missing/product_unresolved` 等明确原因。

mode=none、selected 产品知识缺失、auto 产品未解析、用户知识越权或未发布时，禁止回退全局产品知识。

#### S3-5 统一 telemetry

所有 LLM 调用传递 `context_meta`，至少记录产品、来源、预算、drop 和 fallback。

### 6.3 主要文件

- `services/backend/agent/context_bridge.py`
- `services/backend/agent/context_manager.py`
- `services/backend/agent/scorer_v2.py`
- `services/backend/agent/draft_generator.py`
- `services/backend/agent/draft_chat.py`
- `services/backend/agent/reporter.py`
- `services/backend/api/pipeline.py`
- `services/backend/agent/pipeline_v2.py`

### 6.4 测试

- 每个入口 mock `ContextBridge` 并断言 products/query/purpose；
- none 模式不触发产品知识；
- required 丢失被记录；
- fallback 原因进入日志；
- telemetry 不包含完整知识正文；
- shadow 模式构建新上下文但 LLM 仍使用旧上下文。

### 6.5 退出条件

- 所有生产 PR 入口均已接入；
- 没有入口直接无条件调用全局 `as_system_prompt()`；
- 新旧模式可由开关切换；
- trace 能还原每次上下文来源。

## 7. 阶段 4：轻量文档索引

### 7.1 目标

建立可版本化、可增量更新、可追溯的 JSON 索引，不改变 active 检索行为。

### 7.2 任务

#### S4-1 定义索引 schema

实现 `KnowledgeIndexManifest/DocIndex/SectionIndex`、schema 版本、兼容读取和 JSON 确定性序列化。

#### S4-2 文档发现和分类

- 产品目录映射必须来自 `ProductCatalogService`；
- `overview/market-brief/sales-brief/architecture-brief/tasks` 显式映射；
- `原始文档/` 映射 `raw/fallback`；
- shared 映射 `shared/optional`；
- skills/AGENTS/CLAUDE/README/qa-log 不作为产品事实文档；
- 解析失败必须告警，不能自动落为 cross 后参与全部检索。

#### S4-3 description/summary 生成

已有短 brief 可先用规则摘要或人工审阅的索引元数据；原始长文档使用结构化 LLM 离线生成章节 description/summary；所有结果经过 schema 和事实约束检查。

#### S4-4 增量构建

基于 `content_hash` 只重建变化文档；未变化复用旧元数据；删除/下线文档从新 manifest 移除；构建输出写临时文件，验证后 `os.replace`。

#### S4-5 发布流程对接

```text
验证知识草稿
  → 发布文件到临时版本
  → 构建新索引
  → 校验索引完整性
  → 原子发布知识和索引版本
  → 任务边界加载新版本
```

不得先覆盖线上知识再尝试构建索引。

### 7.3 主要文件

- 新增 `services/backend/agent/knowledge_index.py`
- 新增 `services/backend/scripts/build_knowledge_index.py`
- `services/backend/knowledge_admin/publication.py`
- `services/backend/agent/knowledge_runtime.py`
- `agent-security-briefs/_index/kb-index.json`

### 7.4 测试

- 全量和增量构建结果一致；
- 相同输入索引 hash 稳定；
- 文件变化只重建对应文档；
- raw 进入索引但 tier=fallback；
- skills/管理文档不进入产品事实索引；
- 路径穿越和非法 symlink 被拒绝；
- 用户文档不会写入全局索引；
- 索引构建失败保留旧版本。

### 7.5 退出条件

- 100% 已发布产品必需 brief 可在索引定位；
- 所有 raw 文档有 doc_id，长文档有章节清单；
- 索引构建可重复、可回滚；
- 此阶段仍保持 active 业务行为不变。

## 8. 阶段 5：自适应文档召回和摘要注入

### 8.1 目标

在 `KnowledgeSliceResolver` 内部使用索引选择 optional/fallback 文档，降低无关上下文，同时始终保留 required 文档。

### 8.2 任务

#### S5-1 新增内部 DocumentRetriever

```python
class RetrievalRequest(BaseModel):
    purpose: Literal["score", "draft", "chat"]
    user_id: str | None
    product_ids: list[str]
    query: str
    max_optional_docs: int = 6

class RetrievalResult(BaseModel):
    required_docs: list[RetrievedDocument]
    optional_docs: list[RetrievedDocument]
    fallback_candidates: list[RetrievedDocument]
    trace: RetrievalTrace
```

#### S5-2 实现硬过滤

严格检查产品 ID、purpose、published、tenant/user、allowed tier、文档状态和路径安全。

#### S5-3 实现 required 保留

继续复用 `PURPOSE_DOC_TYPES`，但由索引映射 doc_id。required 缺失时记录，不从其他产品补齐。

#### S5-4 实现首期关键词/BM25 召回

排序字段包括标题、keywords、description、summary、精确术语额外加权和 purpose/doc_type 优先级。候选 ≤8 时不必排序淘汰。

#### S5-5 注入策略

- required 短 brief：注入受预算限制的正文；
- optional：优先注入 summary；
- fallback/raw：只注入章节摘要或候选提示，不默认正文；
- 每块携带 `doc_id/title/source_path`；
- `needs_confirmation` 显式展示给生成模型。

#### S5-6 对接 KnowledgeSliceResolver

保持现有 `resolve()` 对外兼容，增加 `query/index_version/expand_section_ids`。返回结构扩展 `selected_document_ids/expanded_section_ids/retrieval_trace/index_version`。

### 8.3 主要文件

- 新增 `services/backend/agent/document_retriever.py`
- `services/backend/agent/knowledge_slice.py`
- `services/backend/agent/context_bridge.py`
- `services/backend/agent/context_manager.py`

### 8.4 测试

- 产品硬过滤零串扰；
- required 永远保留；
- type 不被错误单值硬过滤；
- 错误码、英文缩写和产品术语可命中；
- 候选 ≤8 不做不必要 LLM 调用；
- optional 超预算按稳定顺序丢弃；
- 空 query 退回 purpose 稳定排序；
- 用户 custom 文档隔离和排序正确。

### 8.5 退出条件

- 文档 Top-N 召回率 ≥95%；
- 跨产品错误注入率 0%；
- required 注入率 100%；
- 上下文 token 相对基线下降 ≥30%；
- PR 人工质量不下降。

## 9. 阶段 6：章节级按需展开和事实引用

### 9.1 目标

PR 需要具体产品事实时，能够展开正确原始文档章节，并让成稿事实可追溯。

### 9.2 任务

#### S6-1 Markdown 章节切分

支持标题层级和稳定 section_id、标题同名消歧、行号或字符 offset、表格/代码块完整性，以及超长章节二级切片。

#### S6-2 展开决策

首期使用确定性触发：用户要求具体参数/案例/部署/版本；query 命中 raw 章节精确术语；summary 标记需展开；草稿事实审核要求证据。LLM 工具调用不是首期唯一决策者。

#### S6-3 获取章节正文

```python
get_document_outline(doc_id)
get_section(doc_id, section_id)
```

校验 doc_id 必须属于冻结产品、当前用户和冻结索引版本。

#### S6-4 事实引用元数据

```text
[KNOWLEDGE_SOURCE doc_id=... section_id=... needs_confirmation=false]
...
[/KNOWLEDGE_SOURCE]
```

草稿保存 `knowledge_citations`，最终 PR 不必展示技术性 doc_id，但后台必须可审计。

#### S6-5 生成后事实审查

复用或增强 `draft_reviewer`：提取产品事实候选，检查是否有知识来源；对数字、案例、部署、版本、竞品声明提高审查等级；缺证据时删除、弱化或标记需确认。

### 9.3 主要文件

- `services/backend/agent/knowledge_index.py`
- `services/backend/agent/document_retriever.py`
- `services/backend/agent/knowledge_slice.py`
- `services/backend/agent/agent_tools.py`
- `services/backend/agent/draft_reviewer.py`
- `services/backend/agent/draft_chat.py`

### 9.4 测试

- section_id 稳定；
- 只允许展开冻结产品章节；
- 不可跨用户读取；
- 每次最多展开配置数量；
- 长章节受 token 限制；
- 参数/案例类草稿缺证据时被标记；
- brief 不足时能命中 raw 相关章节，而不是全文头部。

### 9.5 退出条件

- 需要细节的标注用例章节命中率 ≥90%；
- PR 产品事实有来源率 ≥95%；
- 无依据产品能力新增率 0%；
- 展开失败能安全降级为“资料未覆盖/需确认”。

---

## 10. 阶段 7：评测、Shadow、灰度和全量

### 10.1 Shadow 阶段

新旧链路同时构建上下文，只有旧上下文进入 LLM；记录产品路由差异、新旧文档来源、token 差异、required 缺失、新链路异常和耗时。Shadow 不额外调用昂贵 LLM 重排，除非已设置成本预算。

### 10.2 离线回放

对历史高分文章固定模型和 prompt 版本，新旧链路分别生成，盲评产品相关性、事实准确性和传播质量，并自动检查跨产品术语和无依据数字。

### 10.3 灰度顺序

```text
内部测试用户 100%
  → 5% 生产用户
  → 20%
  → 50%
  → 100%
```

每档至少覆盖一个完整业务周期，并达到门槛后再提升。

### 10.4 停止条件

任一条件触发回滚：跨产品知识注入；selected/none 语义被破坏；无依据产品事实上升；required 文档丢失；错误率或 P95 延迟显著恶化；索引版本与知识版本不一致。

### 10.5 回滚

- 配置切回旧上下文策略；
- 保留新 trace 便于诊断；
- 索引回退到最近成功 manifest；
- 不回滚已发布知识正文，除非正文发布本身有问题；
- 新增模型字段保持向后兼容，不要求数据回滚。

### 10.6 退出条件

- 100% 流量连续稳定；
- 所有核心指标满足门槛；
- 没有跨产品 P0/P1 事故；
- 回滚演练通过；
- 旧全局 fallback 使用率接近 0，并有删除计划。

---

## 11. 阶段 8：按评测升级召回能力

### 11.1 何时引入 LLM 文档重排

产品过滤后 optional/fallback 候选通常 >30、BM25 Top-N 召回足够但前几名排序影响预算、LLM 离线收益显著且延迟费用可接受时启用。只重排 BM25 Top 12 左右，不发送全部文档。

### 11.2 何时引入 embedding

文档增长到千级或章节万级、同义表达导致 BM25 召回不足、混合召回显著提升且模型/重建成本可治理时启用。首选内存/SQLite 或现有数据库能力，无需直接引入 Milvus/Qdrant。

### 11.3 混合排序建议

```text
exact_term_score
BM25(title + keywords + description)
embedding(description + summary)
purpose/doc_type priority
freshness/authority
```

权重通过评测调优，不在代码中凭经验永久硬编码。

## 14. 完成定义

全部满足才视为项目完成：

- 产品路由快照成为评分和 PR 生成的统一输入；
- 单篇、批量、重写和改稿使用同一知识入口；
- selected/auto/none 语义完全一致；
- 产品、租户、发布状态硬过滤无绕过；
- required brief 稳定保留；
- raw 文档可以按相关章节展开；
- PR 中具体产品事实可追溯；
- 资料不足时明确降级，不补写产品能力；
- 新链路 token 明显下降且 PR 质量不下降；
- shadow、灰度、回滚和索引回滚均完成演练；
- embedding 是否引入由评测数据决定，而非作为首期完成条件。
