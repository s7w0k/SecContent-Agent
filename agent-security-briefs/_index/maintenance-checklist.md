# 知识库维护检查清单

## 什么时候使用

每次新增、删除或修改产品 brief、原始文档、共享资料、路由规则、回答规则或 `qa-log.md` 后使用。先记录本次变更范围，再逐项勾选；发现问题时填写证据路径和后续动作，不要只写“待处理”。

结果统一使用：`通过`、`需修复`、`不适用`。

## 快速检查

- [ ] 已确认本次变更涉及的目录和文件，并检查没有顺手修改无关文件。
- [ ] 已检查新增或修改内容是否仍遵守 `CLAUDE.md` 与 `skills/common-rules.md`：不编造功能、交付时间、指标、案例、资质或竞品结论。
- [ ] 已检查本次变更是否需要同步更新 `_index/folder-routing.md`、`README.md` 或 `qa-log.md`；需要时已记录后续动作。

## 结构检查

### README 与真实目录

- [ ] 对照 `README.md` 的“目录结构”和实际目录列表，确认根目录下的 `README.md`、入口文件、`_index/`、`skills/`、产品目录、`shared/` 均存在且名称一致。
- [ ] 对照 `_index/`、`skills/`、`0-产品全景/`、各产品目录和 `shared/` 的文件树，确认 README 没有列出已删除文件，也没有遗漏本次新增的入口或维护文件。
- [ ] 对 README 标注的产品开发状态和资料覆盖状态逐项核实；产品已开发完成不等于所有资料和对外口径都已确认。
- [ ] 若发现目录树不一致，记录“README 路径、实际路径、修复动作”，不得用目录名称相近来代替确认。

### 产品目录最低结构

- [ ] 每个产品目录至少存在 `overview.md`：`1-智能体身份安全/`、`2-智能体安全/`、`3-AI-BOM/`、`4-智能体安全网关/`、`5-ANS/`、`海外版/`。
- [ ] `0-产品全景/` 至少存在 `overview.md`，并保留其产品全景文件；它是索引目录，不替代具体产品的 `overview.md`。
- [ ] 新增产品目录时，已同时确认 `overview.md`、路由归属和资料状态；没有 `overview.md` 的目录不得被路由为常规自动读取入口。
- [ ] 每个产品目录的 `tasks.md`（如果存在）与实际产品状态、资料状态一致；不得把资料待确认写成产品未开发，也不得把未确认内容写成已承诺能力。

### 路由与资料边界

- [ ] `_index/folder-routing.md` 的快速路由表中，所有目标目录都存在；新增目录或产品没有被遗漏。
- [ ] “资料边界提示”与各产品的实际资料覆盖范围一致；产品已开发完成的目录不得标成空模板或未发布。
- [ ] 对具体版本、接口、部署、性能、案例和交付周期等资料缺口保留明确限制，不把资料缺口扩展成产品能力缺失。
- [ ] 新增或调整产品 brief 后，重新检查“核心动词”路由是否仍能把问题导向正确产品；冲突时已写明优先级依据。
- [ ] `skills/` 中仍只描述读取流程和回答方式，没有写入产品事实、未经确认的能力或指标。

## 内容检查

### 待补充与待确认

- [ ] 全文搜索 `待补充`、`待确认`、`资料未覆盖`，逐处检查上下文是否解释了缺口、原因或下一步；没有孤立的“待补充”字样。
- [ ] 每个未完成事项都有可执行信息：涉及产品、问题、应补文件或资料来源、状态；能确定负责人时已填写，不能确定时写 `待定`。
- [ ] 对报价、定价、部署周期、交付周期、客户案例、认证资质和性能数据逐项确认来源；没有来源的内容标为“资料未覆盖”或记入 `qa-log.md`。

### 绝对化表述

- [ ] 全文搜索 `唯一`、`首发`、`领先`、`最全`、`完全覆盖`、`100%`，逐处确认有明确来源、适用范围和时间边界。
- [ ] 无法提供来源的绝对化表述已删除，或改成有边界的事实描述，并保留必要的“以现有资料为准”说明。
- [ ] “首个”“第一”“零风险”“全覆盖”等同类绝对化或保证性表述也已纳入人工复核，不因未命中固定关键词而跳过。

### PPT 指标与承诺边界

- [ ] PPT 中的性能、数量、覆盖范围、部署规格、交付周期、客户案例和效果数据没有直接写成当前承诺。
- [ ] 仍需确认的 PPT 内容已标注：`PPT 提及，需产品确认`；确认状态和来源文件可追溯。
- [ ] brief 的结论没有把 PPT 的演示能力、规划能力或单一案例结果扩大成普遍能力；扩大解释的内容已改为“资料未覆盖”或“推断”。

## 来源与可信度检查

- [ ] 每个 brief 的关键结论都能定位到产品资料或对应 `原始文档/` 的具体文件；至少记录文件路径，必要时记录章节或页码。
- [ ] brief 缺少信息时已按顺序查对应产品的 `原始文档/`；原始文档也没有时没有自行补全，并已记入 `qa-log.md` 或对应 `tasks.md`。
- [ ] 原始资料路径真实存在，引用没有指向已删除、改名或无法打开的文件。
- [ ] 竞品结论、市场热点和时效性内容已标注来源日期；无法从材料直接推出的内容已标为“推断”，没有伪装成产品事实。
- [ ] 来源和表述范围足以支持结论：没有把单个产品、单个版本、单个客户或单张 PPT 的信息写成全产品线的长期事实。

## QA 闭环检查

- [ ] `qa-log.md` 的数据行数量与“总未命中数”一致；不把表头、分隔线和说明文字计入统计。
- [ ] “已补上数”只统计状态为 `已补 brief` 的数据行；“待补充数”与尚未闭环的数据行数量一致，并采用同一统计口径。
- [ ] 每条新未命中记录都包含 8 列：日期、提问角色、产品、问题、原因、状态、应补文件、负责人；没有空白的关键字段。
- [ ] 原因只使用约定值：`brief缺失`、`brief不足`、`原始文档也没有`、`竞品信息缺`、`术语缺`、`市场热点缺`。
- [ ] 状态只使用约定值：`未处理`、`已补 brief`、`需产品确认`、`不纳入范围`；状态为 `已补 brief` 的问题确实已在对应文件补齐。
- [ ] 已处理的问题同步更新状态、应补文件和必要的来源；仍需产品确认的问题没有被写成已确认事实。

## 发布前检查

- [ ] 已完成“结构检查、内容检查、来源检查、路由检查、QA 检查”，每个不适用项都有说明。
- [ ] 已复查本次新增或修改文件中的路径、文件名、表格列数、Markdown 标题和代码块是否可正常读取。
- [ ] 已记录所有 `需修复` 项的负责人、应修改文件和下一步，不以“后续处理”作为唯一动作描述。
- [ ] 清单检查结果与 `qa-log.md`、产品 `tasks.md` 和路由状态没有互相矛盾。
